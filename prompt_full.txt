## GLOBAL RULES (apply to every phase — paste once, keep pinned)

You are a senior staff-level engineer building **NetRaptor-X**, a defensive network-security portfolio project: *"Detect how attacks move through a network, not just which packet looks suspicious."* Target audience: resume review for Cisco, NVIDIA, Rubrik, and general security/ML/backend engineering roles.

**Scope constraints — non-negotiable:**
- Synthetic traffic, isolated local simulation, public datasets, and replayed PCAPs only. Never real malware, credential theft, persistence, exploitation, unauthorized scanning, or destructive payloads.
- All "attacks" are synthetic and safely simulated. Containment actions only ever touch a simulated policy layer — never the real host network.

**Architecture constraints — non-negotiable:**
- The primary intelligence pipeline is **Temporal GNN + Transformer → Fusion → Risk Engine**, not a single tabular classifier. XGBoost/Random Forest/Logistic Regression/MLP/Isolation Forest exist only as comparison baselines, never as the centerpiece.
- The LLM is an investigation/explanation layer on top of the detection model's structured output — it never replaces the detector, never invents evidence, and must distinguish **Observed / Inferred / Recommended** in every report.

**Engineering hygiene — non-negotiable:**
- No fake dashboard data, no fabricated benchmark numbers, no hard-coded model predictions, no `TODO`/`pass`/placeholder detectors left silently — anything deferred must be explicitly documented as a "Future Work" stub, not disguised as done.
- No claims of production deployment or of "detecting real ransomware" — only what the evaluation actually shows.
- After each phase: run tests, run linting, start the relevant services, hit the relevant endpoints, check logs. Don't move on with something basic broken.

**Commit convention** (use for every phase's checkpoint):
```
git add -A
git commit -m "netraptor-x: phase N — <short description>"
```
Each commit should be buildable/runnable on its own — don't leave a phase half-wired across a commit boundary.

## PHASE 3 — Feature Engineering Pipeline

**Goal:** Turn raw flow events into the sliding-window feature set used by everything downstream.

**Do:**
1. `traffic/feature_extractor/` (also usable from `ml/preprocessing/`): centralized config (not scattered thresholds) for sliding windows (10s/30s/60s/5min).
2. Per-window features: traffic volume, packet/byte count, flow duration, packet/byte rate, connection rate, unique destinations/ports, destination/port/connection entropy, failed-connection ratio, internal/external ratio, east-west ratio, burst score, periodicity score, historical deviation, destination novelty.
3. Temporal/behavioral-change features per host: current activity vs. historical mean/variance, short-term and long-term change, rate of change, `traffic_growth`/`destination_growth`/`port_growth`/`connection_growth`.
4. A Feature Worker service that consumes from Kafka, computes features, and writes to the `features` table (and/or Redis for hot rolling-window state).
5. Feature tests: shape tests, edge cases (empty window, single event, burst window), and a test that entropy/rate calculations match hand-computed values on a fixed fixture.

**Algorithmic sub-tasks (real DSA, not bolted on — replaces naive O(n)-per-window recompute):**
- **Monotonic deque sliding-window maximum** for burst score: O(1) amortized instead of rescanning the window every event (classic sliding-window-maximum technique).
- **Fenwick Tree (BIT) or Segment Tree** per host for rolling byte/packet-count sums across the 10s/30s/60s/5min windows: O(log n) update + range query instead of O(n) recompute per event.
- **Count-Min Sketch or HyperLogLog** for approximate unique-destination-count / destination-entropy at higher host counts (e.g. 500-host scale) — document the accuracy/memory tradeoff vs. exact counting, and keep exact counting as the default with the sketch as an opt-in "at scale" mode.

**Acceptance checks:**
- Feature Worker runs continuously against Phase 2's event stream without falling behind (measure and log consumer lag).
- Unit tests cover every feature function with at least one hand-verified expected value.
- A microbenchmark shows the Fenwick-tree/deque-based rolling computation is asymptotically better than the naive recompute baseline on the same data (not just "feels faster" — actual Big-O comparison with numbers).

**Commit checkpoint:** `phase 3 — feature engineering pipeline and feature worker`

## PHASE 9 — Attack Graph Reconstruction

**Goal:** From a suspicious host, reconstruct the propagation path.

**Do:**
1. `backend/app/graph/` (attack-path variant): given a flagged host, walk the communication graph to build source→destination edges with timestamp, evidence, confidence, risk contribution, identifying initial host, propagation path, exposed high-value assets, potential blast radius.
2. Persist to `attack_paths`. Implement `GET /incidents/{id}/attack-path`.

**Algorithmic sub-tasks (real graph DSA, driving the propagation/blast-radius logic — not decorative):**
- **Weighted shortest path (Dijkstra)**: edge weight = inverse of (confidence × risk contribution), so the "most likely propagation path" from the initial host to any downstream asset is a genuine shortest-path computation, not a hand-walked heuristic.
- **Multi-source BFS**: given a set of currently-flagged hosts, compute blast radius (all reachable hosts within the graph) in one pass instead of per-host BFS.
- **Tarjan's algorithm (articulation points / bridges)**: identify hosts/edges whose removal would disconnect the network — surfaced as "critical assets" in the attack-graph output, directly supporting the blast-radius/critical-asset story.
- **Union-Find (DSU)**: maintain connected components of the communication graph incrementally; flag when a new edge merges two previously-disconnected clusters as an additional anomaly signal fed into the risk engine.

**Acceptance checks:**
- Running a Phase 2 lateral-movement or ransomware-like scenario produces a non-trivial multi-hop attack path with evidence on every edge.
- The shortest-path attack path is provably optimal for the given edge weights (test against a small hand-built graph fixture with a known answer).
- Articulation-point detection correctly flags a known critical host in a hand-built fixture graph (e.g. a single gateway host connecting two subnets).

**Commit checkpoint:** `phase 9 — attack graph reconstruction`

**Acceptance checks:**
